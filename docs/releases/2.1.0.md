# 2.1.0

The map gains layers. What was one drawing becomes a stack of two: domains and
capabilities on "Business Domains", and two new kinds of element —
touchpoints and actors — on the "Presentation Layer" above it. The upper layer
can be hidden and the base layer dimmed, so one map answers both "what does this
business do" and "how do people reach it".

The stack is a fixed conceptual model, not a list a map may edit. A domain is
always core and an actor is always presentation; a person reaches the business
through a channel, and a channel reaches a capability. What the two layers mean
is the same in every deployment.

Metadata gains a Type and an opacity, and View mode stops looking like a
disabled Edit mode.

Shipped as `2.1.0-pre.1` first, for a trial run before the release itself.

## Breaking changes

| What | Was | Is |
| --- | --- | --- |
| Document version | `1` | `2` |
| Reading a map file | any 1.x or 2.0.x deployment | 2.1 and later. A 2.0.x deployment refuses a version 2 file. |
| Connectors | `from`/`to`, always capability keys | written under the element that owns them; only capability-to-capability lines stay at the top of the file |
| Elements | `domains` and `capabilities` | `touchpoints` and `actors` alongside them, each with its own keys |

The break is one-way. 2.1 reads every version 1 file there is and puts
everything in it on the base layer, which is what it always meant; what a 2.0.x
deployment cannot do is read a file 2.1 wrote. Keep a 2.0-era export of anything
that has to travel backwards before upgrading.

## Upgrading

Nothing to run. No new environment variable and no schema migration: a document
is `text` in Postgres, so a version 2 document needs no column the table does not
already have.

Stored versions stay as they were written until an owner saves them. A version
saved before the upgrade is version 1 on disk, reads as a base-layer-only map,
and becomes version 2 the next time it is saved. There is no moment where every
map in the database converts at once, and nothing is rewritten behind anyone's
back.

Rolling back to 2.0.x means going back to versions saved before the upgrade, so
take a dump first if any of them matter.

## How it works

### The layers

- Two layers, bottom first: **Business Domains** and **Presentation
  Layer**. They are the model, not the map's own list — a file cannot add one,
  remove one or rename one.
- Which layer an element is on follows from what it is: a domain and a
  capability are core, a touchpoint and an actor are presentation. No element
  carries a layer of its own, so there is nothing that could contradict this.
- The base layer is the bottom of the stack. It can be dimmed but never hidden:
  there would be nothing left under the rest.
- The titles live in the code, not in the file. A map carries each layer's key
  and whether it is hidden or dimmed, and nothing else.

### The layer control

- A control in the bottom left corner of the diagram, in both modes. One row per
  layer, topmost first, each reading `title · selected · dim · eye` with the
  title set against the icons it belongs to.
- The **eye** hides a layer above the base. It is open while the layer is shown
  and struck through while it is hidden.
- The four icons — eye, eye shut, dim, pick — are icon files like every other
  control in the app, so a brand that replaces those replaces these. The row's
  width is held at what its title measures in bold, so picking a layer changes
  nothing about the size of the box.
- The **dim** toggle quietens a layer by one fixed step, multiplied over
  whatever opacity each shape already carries. A dimmed layer stays live: its
  elements hover, select and show their metadata. Dimming is about reading the
  map, never about what can be touched.
- The **selected** box says which layer is being worked on. Only one at a time,
  and only in Edit mode — browsing, there is nothing to add, so the box is not
  there.
  - Edit mode opens on the base layer.
  - Selecting a hidden layer shows it: adding a shape to a layer you cannot see
    would drop it into nowhere.
  - Hiding the layer being worked on moves the work back to the base layer, so
    you are always editing something you can see.
- Hiding a layer drops anything selected on it. A details panel describing a
  shape nobody can see is a panel about nothing.
- Each layer's visibility and dim state are saved in the document, so publishing
  decides what a viewer first sees. Using the control while browsing changes
  that state for the tab only; in Edit mode it changes the saved default, and
  that dirties the document like any other edit — Ctrl-Z and Cancel unwind it.

### Adding a shape

- The Add buttons sit in the top left corner of the diagram, opposite the layer
  control at the foot: making in one corner, reading the stack in the other.
  They offer the kinds the selected layer takes — **Add a domain** and **Add a
  capability** on the base layer, **Add a touchpoint** and **Add an actor** on
  Presentation.
- Every button is as wide as the longest of all four labels, not of the two on
  offer, so switching layers changes what the buttons say and nothing about the
  size of them.
- Each keeps its fill, since a word over a domain's own colour with nothing
  behind it is not a word anyone can read, and shows its border only under the
  pointer or keyboard focus — the way a button in the header does.
- Outside Edit mode there is no selected layer and nothing to add, so the row is
  not there at all.
- The menu panel no longer carries them.

### Touchpoints and actors

Two new kinds, alongside domains and capabilities rather than variants of them.
Each has its own keys, its own defaults and its own validation.

- A **touchpoint** is a rounded rectangle with its label inside. It behaves like
  a capability: a palette colour, a size, a font, and the same snap points
  around its edge.
- An **actor** is a user icon with its label, inside a semi-transparent circle
  with a border. Same snap points as a capability. It arrives at 1.4× where
  every other shape arrives at 1×: a person standing outside the business
  should not be the size of a part of it.
- Neither belongs to a domain. Both carry their own position, and nothing else
  positions them.
- The menu gains a Touchpoints section and an Actors section below the domains,
  and the Details panel gains a section for each kind.

### Connectors

- A line joins two elements strictly down the stack: an actor to a touchpoint, a
  touchpoint to a capability, a capability to another capability. Nothing else
  is a line this model draws, and anything else is refused as it is drawn.
- A line has two ends and no direction, so it is filed under its upper end
  whichever way round it was drawn. An actor's line is always the actor's.
- Lines on the Presentation layer are drawn in a deep teal (`#3c94a3`), a darker
  relative of the touchpoint blue, at the weight of a line that crosses a
  domain. The two greys stay the terrain's.
- Hiding the Presentation layer takes its lines with it. No line is ever left
  running to something that is gone.
- In the menu, a line hangs directly under the element it starts from: a
  capability's lines under the capability, a touchpoint's under the touchpoint,
  an actor's under the actor. One rule for all four kinds, no headings in
  between, and no line listed in two places — which is why there is no longer a
  Connectors section at the foot of the tree.
- A line's row says only where it goes: **to** in the quieter ink, then the far
  end's title, in the far end's own colour. Where it comes from is the row it
  hangs under, so printing that again is noise. This is not a direction on the
  line — a line has none — but a direction read from where the eye already is.
  The whole name is on the pointer and on the row for a screen reader, and in
  the Details panel.
- The Details panel names a line for what it joins: **User interaction**,
  **Touchpoint connector**, and **Internal domain connector** / **Cross-domain
  connector** as a pair. The two capability lines are the same line differing
  only in where the far end lands, so they are named to say that.

### Metadata

- **Type**, on every kind. A picker over a list of choices, with a text input
  that adds a new one.
- Each kind keeps its own list: a domain's types and a capability's types are
  different lists.
- The lists live in the document beside `palette`, so they belong to the map,
  travel with an export and are versioned with it.
- Deleting a choice that is in use is refused, and says how many elements hold
  it ("3 capabilities use 'Engine'"). Nothing is cleared behind the author's
  back, and every Type on the map is always a choice that exists.
- **Opacity**, on every kind, on one scale: 10 to 100 in steps of 10, fading the
  fill and leaving the label readable. A capability and a touchpoint start
  solid; an actor starts at half, so the terrain under it still reads; a domain
  keeps the 20 it always had.

### View mode

- Title, description, owner and Type read as text rather than as greyed-out
  inputs. The value stays legible; it just cannot be changed.
- The icon selector is not shown at all.
- The collapse control beside the metadata tile is not shown.

### The file

- `version` is `2`.
- `layers`: each layer's key, and `hidden` or `dimmed` where either is true.
  No titles — they belong to the model.
- `domains`, `capabilities`, `touchpoints`, `actors`: flat lists, none of them
  naming a layer. Keys stay unique within a kind.
- An actor's lines are written under it as `interactions`, a touchpoint's as
  `connectors`. Each names only its far end and its own shape: the near end is
  the record it sits inside, and the far end's kind follows from the stack.
- `connectors`, at the top of the file, is what no element owns: the lines
  between two capabilities.
- `types`: the choice lists, one per kind, beside `palette`.
- Reading a version 1 file gives a base-layer-only map: no touchpoints, no
  actors, no types.
- A file written by an earlier 2.1 build — per-element layers, layer titles,
  every line flat with typed ends — still reads. The layers are ignored, since
  the kind decides, and the flat lines are filed under their owners. Saving
  writes the shape above.
- `seed/data/versions/v1.json` is in the new shape, with a Presentation layer
  over the BNPL map.

### Versions

- **Rename** is back, on every row of the Versions dialog. 2.0.0 dropped it and
  gave a version a number it kept for good; a version can be called what it is
  for again.
- A version's name is also its address — `?version=` names it — so renaming
  moves it: the old name stops answering and anything pointing at it falls back
  to the published map, saying so. The question asks with that in it.
- Renaming is not saving. The document does not change, nor does when it was
  last saved, so a tab with the version open can still write to it afterwards.
- The name is trimmed, must not be blank, must not hold a slash, and must be at
  most 64 characters. A name another version already has is refused.
- What is published is a pointer to the version, not to its name, so renaming
  the published version leaves it published.
- `v1`, `v2`, `v3` is still what Save as new reaches for, and names that are not
  numbers are counted out of that — so a renamed version neither holds a number
  back nor takes one.

### Export

- **Export SVG** writes what is on screen. A hidden layer is not in the file and
  a dimmed one is dimmed in it, so hiding Presentation and exporting gives the
  clean domain map.
- **Export** (JSON) always writes the whole map, every layer, whatever is on
  screen. A map file is the map, not a picture of it.

### Diagram

- Each layer renders as its own stack of groups — domains, capabilities,
  touchpoints, actors, connectors — and the stacks sit in layer order, so "on
  top" holds for every element on an upper layer rather than most of them.
  Hiding is one attribute on a stack, dimming one opacity.
- Edit handles, the connector draft, hover labels and the text overlay stay
  global, above every layer.
- `layers` in `diagram.js` named the z-order groups. It is `zOrder` now, and
  `layers` means the map's layers.
- The stack itself lives in `rules.js`, not `defaults.js`. A brand may restyle
  its shapes; it may not redefine what the two layers mean.

## Layers vNext

2.1 ships a fixed model rather than a mechanism, and the next layers are a
decision about the model rather than a file a deployment edits. What a third
layer would have to answer first is what connects to it and what it means for
every map already drawn — which is why the stack is code and not data.

What 2.1 deliberately does not ship is a generic architecture stack. Gateways,
secrets management and CI/CD pipelines describe how software is deployed rather
than what a business does, and this is a domain map. Whether the layers after
Presentation are horizontal at all, or the vertical overlays the backlog asks
for (teams, people, observability), is open: an overlay that crosses every layer
is a different mechanism from a layer, and it is not this one.

## Left for later

- A third layer means a release, not a row in a file. That is the trade the
  fixed model makes.
- Type choices can be added, and removed while unused. They cannot be renamed.
- Touchpoints and actors belong to no domain, so nothing groups them but the
  layer they are on.
- A line between two actors, or between two touchpoints, is not a line this
  model draws. A hand-off between two channels has nowhere to go yet.
- Vertical overlays (teams, people, observability) cross every layer and are not
  layers. Still open.

And three things that are wrong rather than missing, found while drawing with
this release and not fixed in it:

- Dragging a capability onto a domain does not make the lobe reach out to
  receive it. The lobe only re-forms for a capability dragged out of that same
  domain and back into it without the button being let go, so a capability
  arriving from elsewhere lands on a shape that has not made room for it.
- A connector's width is a fixed number of map units, so zooming out thins every
  line until the plumbing disappears before the terrain does. It should hold its
  weight on screen at any zoom.
- A line is hard to tap on a phone. What is drawn is a few pixels wide and what
  is hit is the same few pixels; the target needs to be wider than the stroke.
