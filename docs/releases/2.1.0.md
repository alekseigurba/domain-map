# 2.1.0

The map gains layers. What was one drawing becomes a stack: domains and
capabilities sit on a base layer, "Core Business Domains", and a "Presentation"
layer sits above it holding two new kinds of element, touchpoints and actors. An
upper layer can be hidden and the base layer dimmed, so one map answers both
"what does this business do" and "how do people reach it".

Metadata gains a Type, and View mode stops looking like a disabled Edit mode.

Shipped as `2.1.0-pre.1` first, for a trial run before the release itself.

## Breaking changes

| What | Was | Is |
| --- | --- | --- |
| Document version | `1` | `2` |
| Reading a map file | any 1.x or 2.0.x deployment | 2.1 and later. A 2.0.x deployment refuses a version 2 file. |
| Connectors | `from`/`to`, always capability keys | endpoints carry a kind as well, and may name a touchpoint or an actor |
| Elements | `domains` and `capabilities` | `touchpoints` and `actors` alongside them, each with its own keys |

The break is one-way. 2.1 reads every version 1 file there is and lifts it onto
the base layer; what a 2.0.x deployment cannot do is read a file 2.1 wrote. Keep
a 2.0-era export of anything that has to travel backwards before upgrading.

## Upgrading

Nothing to run. No new environment variable and no schema migration: a document
is `text` in Postgres, so a version 2 document needs no column the table does not
already have.

Stored versions stay as they were written until an owner saves them. A version
saved before the upgrade is version 1 on disk, reads as a base-layer-only map,
and becomes version 2 the next time it is saved. There is no moment where every
map in the database converts at once, and nothing is rewritten behind anyone's
back.

Rolling back to 2.0.x means going back to versions saved before the upgrade, so
take a dump first if any of them matter.

## How it works

### Layers

- A map holds an ordered list of layers, bottom first. 2.1 ships two: "Core
  Business Domains" (the base) and "Presentation".
- The list is data, not code. A third layer is a row in the file, not a release.
- The base layer is the one at the bottom. Every map has one, and it cannot be
  hidden.
- Every element names its layer. An element that names none is on the base
  layer, which is what a version 1 file means.
- A capability sits on the same layer as its domain. Moving a domain to another
  layer takes its capabilities with it, so no lobe is ever orphaned from its
  blob and no capability stays bright over a domain that has been dimmed.
- Touchpoints and actors never belong to a domain. They carry their own
  position, and nothing else positions them.

### The layer control

- A control in the bottom left corner of the diagram, in both modes:
  - One row per layer, topmost first, with its title.
  - An eye icon on every layer above the base, which hides it.
  - A dim toggle on the base layer, which cannot be hidden.
- Dimming is one fixed step of opacity over the whole layer, multiplied over
  whatever opacity each shape already carries. A dimmed layer stays live: its
  elements hover, select and show their metadata. Dimming is about reading the
  map, never about what can be touched.
- Each layer's visibility and dim state are saved in the document, so publishing
  decides what a viewer first sees. A map can open with Presentation already
  hidden.
- Using the control changes that state for the tab only, and is never saved. An
  owner in edit mode changes the saved default from the same control, and that
  dirties the document like any other edit.
- The corner it takes is where the "Drag to pan, scroll to zoom" line used to
  be. That line goes, and what it said moves into the **Getting around** dialog,
  which existed for it already.

### Touchpoints and actors

Two new kinds, alongside domains and capabilities rather than variants of them.
Each has its own keys, its own defaults and its own validation.

- A **touchpoint** is a rounded rectangle with its label inside. It behaves like
  a capability: a palette colour, a size, a font, and the same snap points
  around its edge.
- An **actor** is a user icon with its label, inside a semi-transparent circle
  with a border. Same snap points as a capability.
- Both land on the Presentation layer. An actor reaches the business through a
  touchpoint, so hiding Presentation hides the pair of them and leaves the
  domain map behind.
- In the menu bar: **Add a touchpoint** and **Add an actor** below Add a
  capability, and two new collapsible sections, Touchpoints and Actors, below
  domains and capabilities.
- In edit mode a layer picker beside the Add buttons says where a new element
  lands. Domains and capabilities start on the base layer, touchpoints and
  actors on Presentation; the picker overrides either.
- The Details panel gains a Touchpoint section and an Actor section, on the same
  footing as the domain and capability ones.

### Connectors

- An endpoint is a kind and a key, rather than a capability key alone, so a line
  can join any two elements that carry snap points: capabilities, touchpoints
  and actors.
- A connector belongs to the topmost layer it touches. A line from a base-layer
  capability to a Presentation touchpoint is stored in Presentation, and hiding
  Presentation hides the line with it. No line is left running to nothing.
- Domains still carry no snap points and no connectors.
- A version 1 connector reads as two capability endpoints, which is what it was.

### Metadata

- **Type**, on every kind. A picker over a list of choices, with a text input
  that adds a new one.
- Each kind keeps its own list: a domain's types and a capability's types are
  different lists.
- The lists live in the document beside `palette`, so they belong to the map,
  travel with an export and are versioned with it.
- Deleting a choice that is in use is refused, and says how many elements hold
  it ("3 capabilities use 'Engine'"). Nothing is cleared behind the author's
  back, and every Type on the map is always a choice that exists.

### View mode

- Title, description, owner and Type read as text rather than as greyed-out
  inputs. The value stays legible; it just cannot be changed.
- The icon selector is not shown at all.
- The collapse control beside the metadata tile is not shown.

### The file

- `version` is `2`.
- `layers`: the ordered list, bottom first, each with a key, a title and its
  saved visibility.
- `domains`, `capabilities`, `touchpoints`, `actors`: flat lists as before, each
  element naming its layer. Keys stay unique within a kind.
- `connectors`: one flat list, each endpoint carrying its kind.
- `types`: the choice lists, one per kind, beside `palette`.
- Reading a version 1 file gives one base layer holding everything: no
  touchpoints, no actors, no types.
- Writing always writes version 2.
- `seed/data/versions/v1.json` is rewritten in the new shape, with a
  Presentation layer over the BNPL map.

### Export

- **Export SVG** writes what is on screen. A hidden layer is not in the file and
  a dimmed one is dimmed in it, so hiding Presentation and exporting gives the
  clean domain map.
- **Export** (JSON) always writes the whole map, every layer, whatever is on
  screen. A map file is the map, not a picture of it.

### Diagram

- Each layer renders as its own stack of groups (domains, capabilities,
  connectors), and the stacks sit in layer order, so "on top" holds for every
  element on an upper layer rather than most of them. Hiding is one attribute on
  a stack, dimming one opacity.
- Edit handles, the connector draft, hover labels and the text overlay stay
  global, above every layer.
- `layers` in `diagram.js` named the z-order groups. It is `zOrder` now, and
  `layers` means the map's layers.

## Layers vNext

The layer model ships as a mechanism, and 2.1 takes no position on which layers
a business should draw beyond the two it ships. Layers are a list in the file: a
deployment that wants a data layer, an integration layer or a channel split adds
them, names them, and the layer control follows.

What 2.1 deliberately does not ship is a prescribed stack. A generic
architecture stack, with its gateways, secrets management and CI/CD pipelines,
describes how software is deployed rather than what a business does, and this is
a domain map. Whether the layers after Presentation are horizontal at all, or
the vertical overlays the backlog asks for (teams, people, observability), is
open: an overlay that crosses every layer is a different mechanism from a layer,
and it is not this one.

## Left for later

- Layers are added, renamed, reordered and removed by editing the file. There is
  no UI for any of it.
- An element takes its layer when it is created. There is no "move to layer" on
  an element that already exists, so a touchpoint added to the wrong layer is
  deleted and added again.
- Type choices can be added, and removed while unused. They cannot be renamed.
- Touchpoints and actors belong to no domain, so nothing groups them but the
  layer they are on.
- Vertical overlays (teams, people, observability) cross every layer and are not
  layers. Still open.
