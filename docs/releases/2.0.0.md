# 2.0.0

The versions of the map move out of the file store and into Postgres, and who
may change them becomes a role. One deployment is one organization: everyone
lands on the same published version, and owners work on the others.

Shipped as `2.0.0-pre.1` first, for a trial run before the release itself.

## Breaking changes

| What | Was | Is |
| --- | --- | --- |
| Database | none | Postgres, required. No `DATABASE_URL`, no server. |
| Versions | files under `data/versions/` in the store | rows in Postgres, at `/api/versions` |
| `/api/files` | anyone signed in could write | owners only, and it refuses `data/versions/` |
| Who may edit | anyone who could sign in | the addresses in `OWNER_EMAILS` |
| Dependencies | none | `pg` |

## Upgrading a repo built on this package

1. Pin the new version: `npm install domain-map@github:alekseigurba/domain-map#v2.0.0`.
2. Give it a Postgres. The scaffolded `docker-compose.yml` now runs one; a
   deployment elsewhere needs `DATABASE_URL` set and a database to point it at.
3. Set `OWNER_EMAILS` to the people who may edit and publish. Leave it empty and
   everyone who signs in can look while nobody can change anything — the server
   says so at startup.
4. Start it. The first start finds an empty versions table and imports the
   `data/versions/*.json` your store already holds, keeping their names, and
   publishes the one saved most recently. The files stay in the volume as a
   backup; the file API no longer serves them.
5. Nothing else in the repo changes: `server.mjs`, `brand/` and `seed/` keep
   their shape, and `createDomainMapServer` takes `databaseUrl` and `owners`
   alongside its other options.

Rolling back to 1.x means going back to the version files in the store, which
are as they were on the day you upgraded — anything saved since is in Postgres,
so export it first.

## How it works

### Scope and roles

- One deployment is one organization: the whole site shares a single published version.
- Two roles:
  - **Owner** - lands on the published version like everyone else, and can open any other version to view, edit, save, delete or publish.
  - **Viewer** - sees only the published version (the "public view") and can export it as SVG or JSON. Every signed-in user who is not an owner.
- Owners are listed in the `OWNER_EMAILS` env var (`a@x.com,b@y.com`) and matched case-insensitively against the signed-in username. The list is never served over HTTP. No Entra ID role or group claims for now.
- With sign-in off, or through the dev bypass, everyone is an owner.
- With sign-in on and `OWNER_EMAILS` empty, nobody can edit, and the server warns at startup.
- Roles are worked out on each request. There is no users table yet.
- The server enforces roles; hiding controls in the UI is not enough.

### Versions

- Actions: Open, Save, Save as new, Delete, Publish.
- Dropped: Rename, and "Save to another version" (overwriting some other version with the current map).
- Save as new names the version itself: `v1`, `v2`, `v3`, one past the highest number there is. There is no name field, and a name never changes. Two owners reaching for the same number is settled by the unique name, and the loser takes the next one.
- Save as new opens the new version and leaves edit mode, as Save does.
- Published and default are the same thing: one pointer to one version.
- A fresh visit opens the published version for everyone. A refresh keeps what the tab had open. The browser's "last opened version" memory goes away.
- Publish publishes the last saved state. Publishing the open version while it has unsaved changes asks to save first.
- Saving over the published version asks first, because viewers will see the change.
- There is no live refresh: viewers see a newly published version on their next load.
- `?version=<name>` opens a specific version for owners, and the published version keeps the clean URL. A name that does not exist shows a notice and opens the published version.
- A viewer who opens a `?version=` link gets an access-denied page (to revisit later).
- Delete is a hard delete, with these guardrails:
  - The published version cannot be deleted until another one is published.
  - Deleting the version you have open takes you back to the published one, and asks first if it has unsaved changes.
- Two owners saving the same version: the later save is refused ("Saved by A at 14:02 since you opened it") and offered Save as new instead. This is an optimistic check on `updated_at`.

### UI

- An owner-only modal **Versions** dialog, built on the existing `<dialog class="dialog">`:
  - Rows: name, last saved, saved by, a Published badge, and a marker on the version that is open.
  - Row actions: Open, Delete (disabled on the published row), Publish.
  - A Save as new button.
- **Save** stays a one-click header button in edit mode.
- Viewers see neither Edit nor Versions. Export and Export SVG stay.
- Profile: an initials avatar opens a modal popup holding the name, email, role and Sign out.
  - Everything else stays in the header: the map actions (Edit, Save, Versions, Export, Import) and the two help dialogs (Getting around, About).
  - No photo: that would need Microsoft Graph.

### Server and storage

- Keep the Node server (no .NET).
- Postgres is required: the server does not start without `DATABASE_URL`. `pg` becomes the only runtime dependency.
- Only versions and the published pointer move to Postgres. Icons, the brand logo and `settings.json` stay in the file store, so a deployment has both a volume and a database.
- Schema:
  - `versions(id, name unique, document text, created_at/by_name/by_email, updated_at/by_name/by_email)`. The document is `text` or `json`, not `jsonb`, so it keeps its hand-readable formatting, and it is not split into tables.
  - `site`: a single row with `published_version_id`, a foreign key with `ON DELETE RESTRICT`, so the database itself refuses to delete the published version.
- Migrations are numbered `.sql` files in `scripts/migrations/`, run at startup by a small runner with a tracking table (DbUp-style, in Node). Migrating and the first import happen under a Postgres advisory lock, so two replicas starting together cannot both do it.
- API:

  | Endpoint | Who |
  | --- | --- |
  | `GET /api/published` | everyone |
  | `PUT /api/published` | owners |
  | `GET /api/versions` | owners |
  | `POST /api/versions` (the server names it) | owners |
  | `GET`, `PUT`, `DELETE /api/versions/:name` | owners |
  | writes to `/api/files` | owners |

- On first start with an empty `versions` table, the server imports `data/versions/*.json` from the file store, or from `seed/data/versions/` when the store has none.
  - Imported versions keep their names, and names that are not `vN` are counted out when numbering the next one.
  - The most recently saved one is published.
- The imported files stay in the volume as a backup, but `/api/files` refuses everything under `data/versions/`.
- `seed/data/versions/` seeds the versions table, not the file store.

### Branded package (bootstrap)

The consumer contract keeps its shape: `server.mjs`, `brand/` and `seed/`. What changes is the infrastructure around it.

- `createDomainMapServer` gains `databaseUrl` (default `$DATABASE_URL`) and `owners` (default `$OWNER_EMAILS`), like its other options. A scaffolded `server.mjs` does not change.
- `seed/` keeps its layout. `seed/data/versions/*.json` fills an empty versions table, just as it fills an empty store today. `create-app`'s `asSeed()` rewrite of those files keeps working.
- A v1 consumer that upgrades gets its `data/versions/` files imported on first start, so its maps carry over.
- `options.store` (for example S3) still backs icons, the logo and settings. Versions always go to Postgres.
- What a scaffolded repo carries now:
  - `docker-compose.yml` runs a `postgres` service beside the app, published on 5432 so `npm run start:dev` on the host can use it; `npm run db` starts it alone.
  - `dev.env` carries `DATABASE_URL` and `OWNER_EMAILS`.
  - `DEPLOY.md`: the app and a Postgres as two containers in one Azure Container App, on two Azure Files shares, pinned to a single replica.
  - The upgrade command in its README is the version it was scaffolded from, rather than a number written down once and left behind.
- The root `Dockerfile` runs `npm ci --omit=dev`, since `pg` has to be installed. There is still no build step.

### Development

- docker-compose gains a `postgres` service. `dev.env` points `DATABASE_URL` at `localhost:5432`, and the tests create a throwaway database there (`docker compose up -d postgres`, then `npm test`).
- `tests/versions.test.mjs` covers the roles, the naming, a save that lost a race, the published version's guard, the blocked `data/versions/` prefix, a restart and an upgrade from a 1.x store.

## Left for later

- A viewer who follows a `?version=` link is turned away rather than shown the published map. Worth revisiting.
- Roles come from `OWNER_EMAILS` only. Entra ID app roles, and an in-app way to hand out rights, are still open.
- Versions carry no note or description, so the list is names, times and who saved them.
