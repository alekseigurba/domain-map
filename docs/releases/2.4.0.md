# 2.4.0

The map learns who its people are. Where 2.0 had two roles read from an
environment variable — owners, who could do everything, and viewers, who saw
the published map — 2.4 has four, kept in the database and handed out in the
app: **viewer**, **contributor**, **publisher** and the one **administrator**.
Everyone who signs in is a contributor. A list of the people the map knows
comes with it, and the Owner box on a domain or a capability offers them, so
an owner on the map is a person rather than a spelling.

The sandboxes this was designed alongside — a private scope for every
contributor and one shared scope in the open — are [2.5.0](2.5.0.md). The MCP
outline moved on to [2.6.0](2.6.0.md).

## Breaking changes

| What | Was | Is |
| --- | --- | --- |
| Document version | `3` | `4`. A 2.3 deployment refuses a version 4 file. |
| `OWNER_EMAILS` | who may edit and publish, read on every request | read once, into an empty people table: the first address is the administrator, the rest contributors |
| The role that can do everything | *Owner* | *Administrator*, and there is one |
| Everyone else who signs in | a viewer | a contributor |
| Sessions | kept across the upgrade | everyone signs in once more |
| An `auth` of your own | `user(request)` gives `{ name, username, email }` | also `source` and `subject`; without them the email stands in |

The file break is one-way, as 2.1's and 2.3's were: 2.4 reads every version 1,
2 and 3 file there is, with every owner a plain name, and what a 2.3 deployment
cannot do is read a file 2.4 wrote. Keep a 2.3-era export of anything that has
to travel backwards before upgrading.

## Upgrading

One migration, `002-people.sql`, applied at startup like the first. Nothing
else to run.

**Who is what after the upgrade.** The people table is empty when 2.4 first
starts, so `OWNER_EMAILS` is read into it once: the first address becomes the
administrator and the rest contributors, each named by their address until
they sign in. Everyone else who signs in is a contributor. There are no
publishers until the administrator makes some, so publishing is the
administrator's alone on the first day — which is worth doing before anyone
needs to. With `OWNER_EMAILS` empty, the first person to sign in is the
administrator, and the server warns about that at startup; set the variable
before the first start to choose who.

After that first start the variable is not looked at again. Changing it on the
Container App changes nothing; Users & access is where roles are changed, and
the server says so in its startup lines when the variable is still set.

**Everyone signs in once more.** A session from before the upgrade cannot say
which person on the list it belongs to, so it is turned away once, and Entra
signs them straight back in.

**Stored versions** stay as they were written until a contributor saves them,
as with every file version so far: version 3 on disk, version 4 the next time
they are saved. Nothing is rewritten behind anyone's back.

**If the administrator has gone** — left the company without handing over —
`npm run make-administrator -- someone@example.com` makes someone else the
administrator, against `DATABASE_URL`. On a Container App that is
`az containerapp exec` into the running revision; never an update by hand.

## How it works

### The roles

- A ladder, one role to a person, each holding everything the one below it
  does. A **viewer** sees the published map and nothing else. A
  **contributor** opens any version, edits, saves, renames, deletes and
  imports, and talks to the Assistant. A **publisher** also chooses which
  version is the map everyone sees. The **administrator** also decides who is
  what, and there is exactly one — the database itself refuses a second.
- Everyone who signs in is a contributor. Being assigned to the application in
  Entra is the invitation, and someone invited to a map is there to work on
  it; a viewer is what the administrator makes of someone, not what a newcomer
  is. There is no removal: the floor is viewer, and a person who stopped
  signing in sits on the list with when they were last here.
- The role is read from the database on every request, not sealed into the
  session, so a change in Users & access applies at the person's next click.
- The site role is called *Administrator* rather than *Owner*, because every
  domain and capability has an Owner, and one word for two things on one
  screen reads wrong. *Owner* stays the map's word.
- With sign-in off, as in `dev.env`, whoever is there is the administrator:
  there is nobody to tell apart, and a local map has to be workable with no
  configuration at all. The development bypass asks who to be — a name and a
  role on the sign-in screen — so every role can be tried; a name makes a
  person, the first name in is the administrator, and asking for the
  administrator's role afterwards hands it over.

### The people

- A person is one row whatever they sign in with. A second table, `logins`,
  maps each provider's own id for them — Entra's object id, the name typed
  into the bypass — to the person, so someone who arrives by two doors is one
  person, and swapping Entra for another provider later keeps everyone's role.
  The session carries the door and the id, `source` and `subject`; the server
  looks the person up by them.
- A person can be on the list before they have ever signed in: the
  administrator adds them by email, and the first sign-in that carries that
  address — the email claim or the sign-in name, whatever its case — attaches
  the login. The name typed when they were added gives way to the name the
  provider sends. Until then, a typo in the name or the address can be
  corrected on the row; after, both are the sign-in's.
- No directory is read. The list is who has signed in and whom the
  administrator has added; a sync from Entra over Microsoft Graph, which needs
  a tenant administrator's consent, is a backlog item. This keeps the schema
  generic — nothing in it is Entra's but the word `entra` in a login's
  source.

### Users & access

- An entry in the profile popup, beside Sign out, for everyone who works on
  the map: who may do what belongs with who you are. It opens a dialog laid
  out like Versions, a row a person: name, address, role, when they were last
  here. The row that is you is picked out as the open version is.
- Contributors and publishers read it — to see who the publishers are, and
  whom to ask. The administrator's rows carry a select for the role, every
  one but their own, and *Make administrator*, which hands the role over: the
  new administrator has it from that click, and the old one is a publisher.
  At the foot, a form to add someone by name, address and role.
- The administrator's own row reads as it is. The role is handed to another
  row, never picked on this one, and the administrator cannot step down: the
  map always has one.

### The owner of a thing

- The Owner box on an area, a domain, a capability, a touchpoint or an actor
  is still a box to type in, with the people on the list behind it: start
  typing and the names come up, and the address under each. A name that is
  one person's on the list carries their id; a name nobody has — a team,
  someone outside the tenant — carries none, as every owner did until now.
  Two people of one name are neither picked by typing it.
- Under the box, who the id names: their address, or that they are no longer
  on the list. Browsing, the box is quiet as every field is, and a viewer, who
  is not shown the list, has a plain box with the name in it.
- The map keeps who was meant. A person renamed in the directory is shown by
  their new name wherever they own something, and the file catches up on the
  next save: the name in it follows the list, silently, since the file
  following the directory is nobody's change and nothing to undo.
- The Assistant's brief carries the name only, when owners are ticked in, as
  it did.

### The file

- `version` is `4`.
- An element may carry `ownerId` beside `owner`: the people table's id for
  the person the name was picked from. It is written only when there is one,
  so a file whose owners were all typed reads as it did but for the number.
- The number moved for the reason it moved for areas: an app from before
  would read past the id and write the map back without it. Better that it
  refuses the file.

## Known issues

- The names behind the Owner box are a native `datalist`, so how they come up
  is the browser's: Chrome and Edge show the address beside each name,
  Firefox the name alone, and Safari on iOS shows nothing until a letter is
  typed.
- Two people of one name cannot be picked apart in the box. Typing the name
  carries no id; the name is kept, as a typed name is.
- The list behind the Owner box is read once per page load, and again when
  Users & access changes someone in this tab. Someone who signs in for the
  first time while the page is open is on the list at the next load.
- A person who has lost their Entra access stays on the list, since no
  directory is read. Their row says when they were last here; the
  administrator can make them a viewer, and nothing more yet.
