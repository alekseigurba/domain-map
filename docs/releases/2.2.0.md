# 2.2.0

The map gains an **Assistant**: a way to ask an AI about the map, and to bring
what it says back as changes an owner reviews one at a time. It helps write
descriptions, and it grills — the boundaries between domains, the connections,
the actors and touchpoints, how the map compares with an industry standard.

It works with a model behind it, and without one. Two environment variables,
`ASSISTANT_API_URL` and `ASSISTANT_API_KEY`, connect one: anything that answers
chat completions — a free local Ollama, OpenAI, Azure OpenAI, a corporate
gateway — or Anthropic's Messages API. An owner then talks to it in the page.
With neither set, the Assistant writes the prompt and you take it to whichever
AI chat you use, and paste the reply back; that way round works with every tool
there is, stores no key, and sends nothing anywhere unless somebody copies it
out by hand. Either way what comes back is the same reply, checked by the same
rules, shown as the same cards.

The map also learns to say **what the business is**: a description of its own,
which heads every prompt and is what turns a review of "a map" into a review of
this business.

## Breaking changes

None. Map files stay version 2. The map's description is a field a file may
leave out, so a 2.1 deployment still opens a map written here: it reads past the
field, and writes the map back without it.

## Upgrading

Nothing to run: no migration and no new dependency. The skills are files under
`app/skills/`, served like the rest of the app. The four `ASSISTANT_*` variables
are optional, and a deployment that sets none of them gets the Assistant without
a model.

With Postgres running inside the app, as the scaffolded Container App has it, do
not set them by hand: an `az containerapp update` outside the deploy starts a
new revision beside the old one, and two revisions are two Postgres on one data
directory. Set them in the same update that swaps the image.
[BRANDING.md](../BRANDING.md) has the variables; the scaffold's `DEPLOY.md` has
the Container App side.

## How it works

### The loop

- **Assistant**, in the header, swaps the details column for the Assistant and
  back. It is a column rather than a dialog because its cards name shapes, and
  pressing a name has to show that shape on the map behind it. The column is
  wider while it holds the Assistant, 420px for the details panel's 250 — a
  prompt, an answer and a card's reasoning are sentences, not field values. It
  is a token, `--assistant-w`, for a brand that wants another width.
- **Out, by hand.** Pick a skill, and **Copy prompt**. A prompt is the skill's
  task, then the map as a *brief*, then the format to answer in. It stands on its
  own: a chat that has never heard of this app can follow it. Under the button,
  a label says where things stand — **No model connected yet** — and what to do
  about it.
- **Back, by hand.** Paste the reply into **The reply**, prose and code fence and
  all. **Review reply** checks it and lists what it suggests.
- Anyone may copy a prompt — it holds nothing they cannot already see. Bringing a
  reply in and applying it is an owner's, in Edit mode, like every other change.

### With a model connected

- An owner gets **Send** where Copy prompt was. Pick a skill and send it: the
  same task, the same map, the same format to answer in, posted to the model
  rather than copied out. The chip stays pressed, since the next thing wanted is
  as likely the same skill on another domain as a different one.
- **Ask your own** is the one skill with a box to type in — the question itself
  — and Ctrl+Enter there sends it. A standard skill takes no steer: what it asks
  is what its file says, and only *Compare with a standard* and *Trace a flow*
  ask for anything first.
- **Only the exchange in hand is shown**: what was just asked, and the answer's
  summary, in one box under Send. The next Send replaces it and a reload clears
  it. While the answer is awaited the box says *Thinking…* and counts the
  seconds; a model that answers in prose has still answered, and its words are
  shown there in full; one that failed says so in its API's own words.
- The answer's **cards join the review below**, beside any still waiting from
  earlier answers.
- **Nothing of the conversation is written down**, and none of it is shown but
  the last exchange. The model is still sent the last six turns — what was asked
  and what it answered, without the map as it stood then — from this page's
  memory and no further, so *and the second one?* means something. A soft line
  under the exchange is the only sign of that, and the way out of it: *2 earlier
  turns remembered · Start over*. A reload forgets them; so does opening another
  version. The cards are another matter: they are the review, and stay with the
  tab as they do for a pasted reply.
- **Every turn sends the map afresh**, because applying a card from the last
  answer has changed it. The two formats are the system prompt, which never
  changes, so a model that caches a prefix pays for them once.
- The page does not announce where a message goes. **Send's tooltip** does, for
  whoever wonders: the model and the host. A draft is an owner's secret, and
  pointing the Assistant at a hosted model sends it out of the building — that
  is a thing to decide when the variables are set, not each time Send is
  pressed.
- Asking is only asking, so **Send works while browsing**; applying a card still
  waits for Edit.
- A **viewer never gets Send**, and is not told whether there is a model. They
  keep the skills and Copy prompt, and spend nobody's tokens.
- **Use another chat**, a quiet link under Send, brings Copy prompt and the
  reply box back — for the day the connected model is down, or a different one
  is wanted.

### The model behind it

- The server is only ever a relay: `POST /api/assistant/chat`, an owner's. The
  page writes the prompt, because the page is where the map and the skills are;
  the server posts it on with a key the browser never sees, and hands back text.
  `/api/me` tells an owner the host and the model, and never the key.
- `ASSISTANT_API_URL` is posted to **as it stands**, so an Azure deployment URL
  with its `api-version` works as well as a bare `/v1/chat/completions`. The
  key goes as `Authorization: Bearer` and as `api-key`, since a gateway wants one
  and Azure the other. `ASSISTANT_MODEL` is sent when it is set.
- A URL on Anthropic's host, or ending in `/messages`, is spoken to as the
  **Messages API**: `x-api-key`, the version header, the system prompt as a field
  of its own, room for a 16,000-token reply, and `claude-opus-5` unless
  `ASSISTANT_MODEL` says otherwise. First-party, a declined request is re-run on
  the fallback Anthropic recommends; a gateway is not sent a parameter it would
  reject. `ASSISTANT_API_STYLE` — `openai` or `anthropic` — settles it where the
  URL does not.
- Plain `fetch` for both, so `pg` stays the only dependency a consumer repo
  installs. One more try on a rate limit or an overloaded model, after as long
  as it asks for; two minutes, then the wait is given up. A key the model
  refuses is said to be the deployment's to fix, in the API's own words.
- `options.assistant` on `createDomainMapServer` replaces all of that with a
  `{ chat, host, model }` of the consumer's own, the way `options.auth` does.
- With sign-in off, or `OWNER_EMAILS` empty, everyone is an owner and any of them
  can send the map out on the server's key. The server says so at startup.

### The brief

- The map with its drawing left out: titles, descriptions, types, which domain
  holds what, and every line with what kind of line it is — inside a domain,
  across a boundary, from a touchpoint, from an actor. No positions, colours or
  sizes: a model asked about boundaries has no use for where a blob sits, and no
  business moving it.
- The **whole** map goes every time, with the subject of the task marked. A
  boundary cannot be judged without the neighbours.
- **Owners' names stay behind** unless *Include owners' names* is ticked. They
  are the one personal thing on a map, and only questions of ownership need them.
- A shape is named to the model as `capability:fraud-detection` — its kind, and
  its title the way a permalink spells it. A line is named by its two ends.

### Skills

Fourteen, in three rows. A skill follows the selection: **Describe** is about
the capability you have picked, **Grill the boundaries** about the domain you
have picked or, with nothing picked, the whole map. One that needs a selection
it has not got cannot be pressed, and says what to pick.

- **Write** — *Describe the business*, *Describe*, *Fill the blanks*, *Tighten
  the wording*, *Propose capabilities*, *Start a map*.
- **Grill** — *Grill the boundaries*, *Grill this capability*, *Find missing
  connections*, *Question the connections*, *Review the presentation layer*,
  *Compare with a standard*, *Trace a flow*.
- **Ask** — *Ask your own*: your question, with the brief and the reply format
  wrapped round it, so the answer still comes back as cards.

Each skill is a file, `app/skills/<name>/SKILL.md`, in the agent-skills form: a
`name` and a `description` in the front matter, the task as the body. The app
reads that folder to build its prompts, and an agent pointed at the folder loads
the same files — there is one copy of every prompt. Its `metadata` says what the
skill works on, what it asks for first, and **which operations its reply may
use**.

### What a reply may do

A reply is one JSON object holding suggestions, and a suggestion holds
operations from a short closed list:

| Operation | What it does |
| --- | --- |
| `describe` | Writes the description of a shape, a line, or the map itself. |
| `rename` | Gives a shape another title. |
| `set-type` | Gives a shape one of the map's own Type choices. |
| `add-domain`, `add-capability`, `add-touchpoint`, `add-actor` | Adds a shape, placed where the Add buttons would place it. |
| `move-capability` | Hands a capability to another domain. |
| `connect` | Draws a line, if it is one the model can draw and the two are not joined already. |

- **Nothing is removed.** There is no remove, no disconnect and no merge. A model
  that thinks something should go says so in a *note* — a suggestion with no
  operations — that names the shape, and the owner deletes it by hand.
- **Nothing is moved about.** Position, colour, size, layers and the palette are
  not operations. Where a shape sits is the owner's meaning, not the model's. The
  one liberty taken: a domain added from a reply wears a swatch no other domain
  does, since a map started from a reply gets six at once.
- **A skill is held to its own list.** *Describe* may describe and nothing else,
  so a reply to it that renames something is refused, whatever the chat was
  talked into.
- A suggestion may use the shapes it makes — a capability added to the domain it
  has just added — by giving them a `new:` name. The name means nothing outside
  that suggestion.

### Review and apply

- Every suggestion is a **card**: what it is, why, what applying it would do in
  plain words, and the shapes it names as chips that select them on the map.
- A reply comes from a chat nobody vouches for, so every line of it is checked
  against the same rules the editor keeps — title and description lengths, which
  kinds connect, the map's Type choices. **One operation that does not hold
  refuses its whole card**, and the card says why: half of a split is worse than
  none of it.
- Keys are resolved to shapes the moment a reply is brought in, so a rename
  applied from one card cannot break the cards after it. Each card is asked again
  whether it still holds just before it is applied, since the map moves on under
  a review.
- **Apply** is one undo step, however many operations the card holds. **Apply
  all** applies everything left that can be, each as its own step.
- A citation of a standard is shown *worth checking*. A model cites what sounds
  right more readily than what is.
- The cards are kept with the tab, like the edit session, so a review of thirty
  cards survives a reload. Opening another version forgets them, for the reason
  it clears the undo history: they name shapes that are gone.

### What the business is

- The map has a description of its own, up to 2000 characters: the industry, who
  the customers are, what is in scope and what is not, the standards the map is
  weighed against.
- It is read and written in the details panel with **nothing selected**, under
  **Map** — nothing selected is the map itself. It is part of the map, so it is
  saved, versioned, exported and undone with it, and everyone who sees the
  published map can read it.
- The Assistant does not hold a copy of the field. While the map has no
  description it says, in one line, that a review will be generic without one,
  and offers *Describe the business* first: the skill that drafts it from what
  is on the map, for the owner to correct. Once the map says what it is, the
  line goes.

## Still to do in 2.2

An outline, to be put into the owner's words. None of it is built; each is
written up above, and its bullet removed, as it ships.

- Skills open to a consumer repo: `skills/*` joins the override table in BRANDING.md, so a brand can add "check against our capability glossary" or reword the standard ones. The operations stay the package's.
- Reference packs: a file in the store (`data/assistant/references/*.md`) that *Compare with a standard* writes into the prompt, so a citation comes from the file rather than from the model's memory. An internal capability glossary goes in the same way.
- Streaming, if the wait turns out to matter: the summary as it is written, the cards once they are whole.
- Limits an owner cannot talk past: one request at a time per owner on the server, not only per tab, and a count of what was spent.
- A review kept on the server rather than in the tab, so another owner can pick it up: a `suggestions` table in Postgres (a migration), which MCP's `submit_suggestions` in [2.6.0](2.6.0.md) queues into as well. A conversation is deliberately kept nowhere: only the exchange in hand is shown, and none of it is written down.

## What it does not do yet

- **Let an outside agent reach the map.** That is MCP, and [2.4.0](2.4.0.md).
- Until the list above is worked through: an answer arrives whole rather than
  streamed, so the exchange shows *Thinking…* and the seconds; `app/skills/` is
  internal, and a consumer repo cannot add or reword a skill; and the cards
  belong to the tab, so another owner does not see them.

## Known issues

- Opening the Assistant narrows the stage by 170px and does not refit the map, so
  a map fitted to the wider stage is clipped at its right-hand edge until it is
  panned or *Fit to screen* is pressed.
- A prompt for the example map is about 25 thousand characters, most of it the
  two format descriptions and the brief. That is well inside what current chats
  take, and more than some free ones like in one message.
